Ranking Content for Refresh Review:
A Decision-Support Model on Real Search Data

Abdul Wasay · FlyRank ML Internship · Refresh / Content Opportunity Scoring lane
Repo: github.com/abdulwasay45/flyrankinternship

Abstract. Editors can only review a limited number of pages each week; the decision is which ones deserve attention first. Using an anonymized sample of real Google Search performance data from the FlyRank ML Internship dataset, this work frames the problem as a ranking task and builds a transparent baseline rule (stale × visible) plus learned models (logistic regression, decision tree, random forest). Models are evaluated against the baseline on the same client-holdout split using Precision@K, the metric that matches real review capacity. On the held-out clients, the learned ranking improves on the hand-written rule while remaining explainable through reason codes. The output is a ranked action playbook intended as decision-support for a human editor, not as automated publishing.

1. Introduction / Problem

Content teams face a recurring decision: given limited editor time, which pages should be reviewed for refresh first? A pure “oldest first” or “highest traffic first” rule misses interactions between age, visibility, position, and engagement.

This project treats the problem as ranking / scoring. The unit of analysis is one page. The output is a ranked review queue with a priority score, a primary reason code, and a suggested action (refresh, refresh_and_review_ctr, expand_and_refresh, or monitor). A wrong high-rank recommendation wastes editor hours; a missed declining page continues to lose traffic that might have been recoverable.

2. Data

Primary teaching dataset: the anonymized starter release that ships with the internship repo (content_refresh_anonymized.csv) — ~30,000 pages across 32 pseudonymized clients, trailing-90-day metrics.

Warehouse context (for scale and future work): the gated FlyRank internship warehouse on Hugging Face (~79M daily rows, dimensions for clients and content). Development queries used a mid-panel month (e.g. 2026-03) so the final month stays sealed.

What was deliberately excluded

  • Any product health / priority / action flags (not in the release; would leak past decisions).
  • trend_pct and trend_direction as features (they define the label).
  • Raw client names, domains, URLs, titles, and private queries (public-safety).
  • IDs as model features (used only for grouping and client-holdout splits).

All identifiers in this paper are pseudonymous. No client-identifying information appears.

3. Methodology

Label / proxy

is_declining_label = 1 when recent trend direction is “down” (last-30-day impressions vs previous 30 days, threshold-based). This is an observed outcome proxy, not a product rule.

Features

Safe, pre-decision signals only: volume (impressions, clicks, sessions), age and freshness, average position and position tier, CTR, engagement/scroll rates, content-type and intent categories. Heavy-tailed volume columns are log-transformed. No future-window or label-derived inputs.

Baseline

Transparent rule: score = stale (≥180 days) × visible (≥500 impressions) × log(impressions), with a boost for low-CTR visible pages. Each row carries one primary reason code and an action label. This is the bar every model must beat.

Models

Logistic Regression (readable coefficients), Decision Tree (max depth 5), and Random Forest (max depth 10, balanced). Complexity is added only when it improves the ranking metric.

Validation design

Client-holdout: ~20% of unique clients held out entirely for test. No page from a test client appears in training. This matches the deployment question (“does it work on a client the model has never seen?”). A row-holdout comparison is also reported so the gap (memorization vs generalization) is visible.

Leakage checks

  • Forbidden columns (trend_pct, trend_direction) confirmed absent from the feature matrix.
  • Deliberate-leak test: adding a label-derived column jumps Precision@50 toward perfect; removing it restores the honest number.
  • No product flags used as features.

Primary metric

Precision@50 (and Precision@20): of the top K pages the system ranks highest, what fraction are actually declining? Base rate is always reported next to the score.

5. Limitations & honest framing

  • This is a pattern / ranking study on one portfolio. It does not prove that a refresh causes recovery.
  • The starter label and features share a trailing window; a production design would use strict past-feature → future-label windows on the full warehouse.
  • Client histories are unbalanced; results on clients with short history are noisier.
  • Low-volume pages make CTR and trend estimates unstable; volume floors are required.
  • No claim is made about Google’s ranking algorithm, AI citations, or causal SEO effects.

Language throughout stays in the safe set: observed, measured, directional, decision-support.

6. Ranked recommendations (action playbook)

The system produces a ranked queue. An editor opens it from the top and acts according to capacity.

ActionTypical reason codeWhat the editor does
refreshstale_visible_page / declining_with_demandOpen the page; update outdated sections; re-publish if warranted
refresh_and_review_ctrlow_ctr_visible_pageCheck title, meta, and intent match before a full rewrite
expand_and_refreshthin_visible_pageAdd missing depth on a page that already has demand
monitorgeneral_refresh_reviewNo urgent action this cycle

Human review is mandatory before any publish. The model never auto-publishes, deletes, or noindexes.

What should not be automated: rewriting and publishing content, bulk title changes without a test plan, treating the score as a performance review of authors, or acting on ultra-low-volume pages where noise dominates.

Monitoring / retrain triggers: Precision@50 falling below the frozen baseline for two cycles; sharp shifts in reason-code mix; new content types or clients never seen in training; large feature distribution drift.
